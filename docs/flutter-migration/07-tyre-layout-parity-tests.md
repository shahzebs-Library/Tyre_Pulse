## 1. The position vocabulary problem, resolved

**This section is the reason the artifact exists.** Spec rule 10 forbids
renaming tyre positions, and spec section 22 lists 23 identifiers it calls
"canonical storage keys". That list is accurate about a vocabulary that exists,
but it is **not the vocabulary the inspection write path uses**, and a Flutter
port that treats it as one will silently corrupt every inspection.

### 1.1 There are THREE vocabularies, not one

VERIFIED. `mobile/lib/tyreDiagramLayouts.ts:421-426` says so in its own words:

> The app carries two position vocabularies:
>   diagram ids (this file / web):  FL, RLo, F1L, R2Ro ...
>   lib/types.ts TYRE_POSITIONS:    FL1, RL1..RL4, SL/SR, AxleL1, Spare ...

and a third is introduced by `legacyPositionCode` at
`mobile/lib/tyreDiagramLayouts.ts:364`.

| # | Vocabulary | Example ids | Defined at | What it is |
|---|---|---|---|---|
| V1 | **Diagram slot id** | `FL`, `RLo`, `F1L`, `R2Ro` | `mobile/lib/tyreDiagramLayouts.ts:57-252` (`LAYOUTS[].tyres[].id`) | **The storage key for `inspections.tyre_conditions`.** Also the diagram hit-test key |
| V2 | **Canonical GCC code** | `LHF1`, `LHCO`, `RHR1-O` | `mobile/lib/tyreDiagramLayouts.ts:350-362`, mirrored `src/lib/tyrePositions.js:163-175` | **The storage key for `tyre_records.position` / `tyre_position`.** Also the DISPLAY LABEL of a V1 slot |
| V3 | **types.ts position set** | `FL1`, `RL1`..`RL4`, `SL`, `SR`, `AxleL1`, `Spare` | `mobile/lib/types.ts:408-433` (`TYRE_POSITIONS`) | A parallel set used by two read-side callers. **Not written by the capture screen** |

The decisive quote is `src/lib/tyreBay.js:178-192`, which states the split and
the evidence for it:

> Two vocabularies live in the data and both are right where they are written.
> `tyre_records.tyre_position` holds the ERP/canonical code the business uses
> (LHF1, RHRI, LHCO); `inspections.tyre_conditions` is keyed by the mobile
> capture app's internal slot id (F1L, R2Ri, R1Lo). **Eight live inspections
> store both against the same wheel, which is what proves the pairing rather
> than guessing it.** ... The stored value is NEVER rewritten - only what we
> show. The mobile app still writes and reads F1L keys, and offline records in
> flight still carry them.

`src/lib/tyrePositions.js:16` states the other half independently:

> The codes double as a stable storage key (tyre_records.position) and a
> human-readable label via describePosition().

**So both V1 and V2 are storage keys. They are storage keys for DIFFERENT
TABLES.** Neither is "the render slot id" and neither is "the database key" -
that framing does not survive contact with the source.

### 1.2 The spec's own list is V3, and only 4 of its 23 ids are real slots

VERIFIED by executing the extraction against `LAYOUTS`. The 13 production
layouts contain **22 distinct slot ids** in total:

```
FL, FR, RL, RR, RLo, RLi, RRi, RRo,
F1L, F1R, F2L, F2R, F3L, F3R,
R1Lo, R1Li, R1Ri, R1Ro, R2Lo, R2Li, R2Ri, R2Ro
```

Cross-checking the 23 identifiers listed in spec section 22 against that set:

| Spec id | A real diagram slot? |
|---|---|
| `FL`, `FR`, `RL`, `RR` | **YES** (4 of 23) |
| `FL1`, `FR1`, `FL2`, `FR2` | no |
| `RL1`..`RL4`, `RR1`..`RR4` | no |
| `SL`, `SR` | no |
| `AxleL1`, `AxleR1`, `AxleL2`, `AxleR2` | no |
| `Spare` | no |

And 18 real diagram slots are absent from the spec's list entirely: `RLo`,
`RLi`, `RRi`, `RRo`, `F1L`, `F1R`, `F2L`, `F2R`, `F3L`, `F3R`, `R1Lo`, `R1Li`,
`R1Ri`, `R1Ro`, `R2Lo`, `R2Li`, `R2Ri`, `R2Ro`.

**There is no `Spare` slot, no `SL`/`SR` lift slot and no `AxleL1` trailer slot
in ANY of the 13 layouts.** `grep -c "id: 'SP"` over
`mobile/lib/tyreDiagramLayouts.ts` returns **0**. Spec section 23's
`spareSlots` field therefore models something the production data does not
contain. `mobile/lib/tyreCompleteness.ts:55-57` states the consequence
deliberately:

> The layouts carry no spare slot, so a spare is never "missing" either: nobody
> is sent to inspect a spare that may not be fitted.

### 1.3 Where the conversion happens, and in which direction

VERIFIED.

```
V1 slot id  --legacyPositionCode(layoutKey, id)-->  V2 canonical code
V2 code     --canonicalToSlotId(typeHint, code)-->  V1 slot id
```

| Direction | Function | Location | Notes |
|---|---|---|---|
| V1 -> V2 | `legacyPositionCode(vehicleTypeKey, id)` | `mobile/lib/tyreDiagramLayouts.ts:364-371`; web `src/lib/tyrePositions.js:177-184` | **Type-aware.** A Tri-mixer overrides the first rear axle to the CENTER axle |
| V2 -> V1 | `canonicalToSlotId(vehicleTypeKey, positionCode)` | `src/lib/tyreBay.js:218-235` | **Web only. There is no mobile implementation.** Inverts V1 -> V2 by scanning the resolved layout's slot set |
| V2 normalisation | `canonicalCode(raw)` | `src/lib/tyrePositions.js:107-115` | Folds `LHF1` / `L H F 1` / `LF1` to one form. Dash before I/O only when an axle number is present |

The V1 -> V2 map, VERIFIED from `mobile/lib/tyreDiagramLayouts.ts:350-362`:

```
_LEGACY_BASE
  FL   -> LHF1     FR   -> RHF1     RL   -> LHR1     RR   -> RHR1
  RLo  -> LHRO     RLi  -> LHRI     RRi  -> RHRI     RRo  -> RHRO
  F1L  -> LHF1     F1R  -> RHF1     F2L  -> LHF2     F2R  -> RHF2
  F3L  -> LHF3     F3R  -> RHF3
  R1Lo -> LHR1-O   R1Li -> LHR1-I   R1Ri -> RHR1-I   R1Ro -> RHR1-O
  R2Lo -> LHR2-O   R2Li -> LHR2-I   R2Ri -> RHR2-I   R2Ro -> RHR2-O
  R3Lo -> LHR3-O   R3Li -> LHR3-I   R3Ri -> RHR3-I   R3Ro -> RHR3-O

_LEGACY_TRIMIXER   (applied ONLY when the layout key contains "tri" or "mixer")
  R1Lo -> LHCO     R1Li -> LHCI     R1Ri -> RHCI     R1Ro -> RHCO
  R2Lo -> LHRO     R2Li -> LHRI     R2Ri -> RHRI     R2Ro -> RHRO
```

Note `R3Lo`..`R3Ri` are present in the map but **no layout uses them** - they
are provision for a future 3-drive-axle layout. Port them; do not treat their
absence from `LAYOUTS` as an error.

### 1.4 The label is DERIVED at module load, never stored

VERIFIED. `mobile/lib/tyreDiagramLayouts.ts:376-378` mutates the layout data at
import time:

```
Object.entries(LAYOUTS).forEach(([typeKey, layout]) => {
  layout.tyres.forEach(t => { t.label = legacyPositionCode(typeKey, t.id) })
})
```

The web does the identical mutation at `src/components/VehicleTyreDiagram.jsx:1470`.

**Rule for Flutter: `TyreSlot.label` is a computed property, not a stored
field.** Hard-coding the label beside the id is exactly what the Kotlin app did
(section 6), and it makes the type-aware Tri-mixer override impossible to apply
to a layout it was not hand-written for.

### 1.5 A live read/write vocabulary mismatch inside the Expo app

VERIFIED, and this is a defect the Flutter port must not carry over.

| Path | Call | Vocabulary produced |
|---|---|---|
| Inspection capture (WRITE) | `mobile/app/(app)/inspection/new.tsx:321` `diagramPositions(v.vehicle_type)` | **V1** - `F1L`, `R1Lo`, ... |
| Inspection detail (READ) | `mobile/app/(app)/inspection/[id].tsx:89` `getPositionsForVehicle(insp.vehicle_type)` | **V3** - `FL1`, `RL1`..`RR4`, `Spare` |

For a Tr-Mixer the write path stores 12 keys
(`F1L,F1R,F2L,F2R,R1Lo,R1Li,R1Ri,R1Ro,R2Lo,R2Li,R2Ri,R2Ro`) and the read path
asks for 13 different ones
(`FL1,FR1,FL2,FR2,RL1,RL2,RL3,RL4,RR1,RR2,RR3,RR4,Spare`). **The two sets do not
intersect at all.**

The damage is contained by two things and only two: `matchPositionsToLayout`
(`mobile/lib/tyreDiagramLayouts.ts:491-549`) maps EITHER vocabulary onto layout
slots, so the DIAGRAM still draws correctly; and the condition list below the
diagram iterates `Object.entries(conditions)`
(`mobile/app/(app)/inspection/[id].tsx:183`) rather than the position array, so
the readings still list. The V3 array is used only to decide whether to render
the diagram at all and what to hand it.

**Report before changing: the Expo app is production and this document is an
audit, not a patch.** For Flutter the rule is simple.

**Rule for Flutter: `diagramPositions()` (V1) is the ONLY position-set producer.
Do not port `getPositionsForVehicle` or `TYRE_POSITIONS`.** V3 has two callers
(`inspection/[id].tsx:89` and the dead `tyreLayout.ts`) and is not a storage
vocabulary anywhere.

### 1.6 The rule, stated once

1. `inspections.tyre_conditions` is keyed by **V1**. Write V1. Read V1.
2. `tyre_records.position` / `tyre_position` is keyed by **V2**. Write V2. Read V2.
3. Convert with `legacyPositionCode` / `canonicalToSlotId`. **Never rewrite a
   stored value.** `src/lib/tyreBay.js:197-200`: a wheel that cannot be placed
   keeps its own name, because "an invented one sends a fitter to the wrong
   tyre, which is worse than an unfamiliar one."
4. Accept either vocabulary on input at the diagram boundary
   (`matchPositionsToLayout`), because offline records in flight carry V1 and
   ERP-sourced rows carry V2.

## 3. Resolver ORDERING rules

VERIFIED from `mobile/lib/tyreDiagramLayouts.ts:265-347`. `resolveOne` returns
`null` when nothing matches, and `resolveVehicleType` is
`resolveOne(vt) ?? resolveOne(assetNo) ?? 'Pickup'` (line 346). **The null is
load-bearing**: it is what lets the asset number be tried instead of settling
for a Pickup.

Each rule below is stated as a testable assertion with the input that regresses
if the order is wrong.

| Rule | Order position | Assertion | Regression input if reordered |
|---|---|---|---|
| **R1** Exact layout-key match, case and separator insensitive | 1st, line 270-273 | `TR-MIXER`, `Tr-Mixer`, `tri mixer` all resolve to `Tri-mixer` | Any layout key with a space or dash stops matching itself |
| **R2** Asset-code prefix **requires a digit after the letters** | 2nd, line 280-291. Regex `^([A-Za-z]{2,3})\s*\d`, prefix taken as `.slice(0,2)` | `PL077` -> `Pickup`; `PLACING BOOM` -> NOT Pickup | Drop the `\d` and `PLACING BOOM` reads as a `PL` pickup and draws 4 wheels. RECORDED as the real 2026-08-05 defect |
| **R3** N-Wheeler names run BEFORE the `wheel` keyword | 3rd, line 295-302 | `10 WHEELER` -> `Truck 6x4` (10) | `wheeler` contains `wheel`, so it falls into the 4-tyre `Wheel loader`. Stated in the source comment |
| **R4** `stationary` guard sits ABOVE the `pump` catch-all | line 312, before line 318 | `STATIONARY PUMP` resolver output is `Pickup`, never `Concrete pump` | Move it below and a wheel-less skid pump draws 14 wheels |
| **R5** `linepump` before `spiderpump` before generic `pump` | lines 315, 317, 318 | `LINE PUMP` -> `Line pump` (12); `SPIDER PUMP` -> `Truck 6x4` (10); `PUMPS` -> `Concrete pump` (14) | Collapse them and the whole pump family becomes the 14-tyre MP pump. | **R7** `boom`/`placing` -> `Concrete pump` | line 307 | See divergence note below | - |
| **R8** `tanker` before `trailer` before `crane`/`truck` | lines 327, 329, 331 | `SLURRY TANKER` -> `Tanker` (6), not `Skid loader` | Without R2's digit requirement `SL`urry reads as a skid loader. Pinned by the existing test at `tyreDiagramLayouts.test.ts:34` |

### 3.1 R7 is a real web/mobile divergence. VERIFIED by execution.

Mobile line 312 guards only `stationary`. The web equivalent
(`src/lib/vehicleTyreLayout.js:143`) guards **both**:

```
web:    if (s.includes('placing') || s.includes('stationary')) return 'Pickup'
mobile: if (s.includes('stationary'))                          return 'Pickup'
```

Executing both resolvers over 40 inputs produced exactly two divergences:

```
DIVERGE "PLACING BOOM" | mobile=Concrete pump tyreless=true | web=Pickup tyreless=true
DIVERGE "PLACING"      | mobile=Concrete pump tyreless=true | web=Pickup tyreless=true
```

**It is INERT today** because `isTyrelessEquipment` catches `placing` at
`mobile/lib/tyreDiagramLayouts.ts:393` and short-circuits before the resolver is
consulted - both platforms correctly draw zero wheels. But the mobile source
comment at lines 308-311 claims a defensive stop exists so that "any caller that
skips that check can never fall through to the 'pump' branch below and draw 14
tyres", and **for `placing` that claim is false**.

**Rule for Flutter: port the WEB form of the guard**
(`placing` OR `stationary`), which is the one whose behaviour matches its stated
intent. Pin it with test 22.

## 4. Geometry model

### 4.1 What the source actually provides

VERIFIED. A production layout entry is exactly this shape
(`mobile/lib/tyreDiagramLayouts.ts:40-54`):

```
DiagramLayout { emoji, viewH, bodyKey, tyres: TyreDef[] }
TyreDef       { id, x, y, w, h, label }
```

Coordinates are absolute, hand-authored, in an SVG user-space where the viewBox
is `minX -10, width 220, minY -5, height viewH + 10`
(`mobile/components/VehicleTyreDiagram.tsx:1269-1274`). Usable x is 0..200 and
centre x is 100 (`mobile/lib/tyreLayout.ts:16-17`).

### 4.2 Mapping onto the spec section 23 model

| Spec field | Provided by source? | How Flutter obtains it |
|---|---|---|
| `VehicleLayoutDefinition.vehicleType` | YES | The `LAYOUTS` key returned by `resolveVehicleType` |
| `.bodyClass` | PARTIAL | `bodyKey` is one of 8 art keys (`mobile/lib/tyreDiagramLayouts.ts:30-38`): `pickup`, `canter`, `triMixer`, `concretePump`, `wheelLoader`, `bus`, `tata`, `ashokLeyland`. It is an ARTWORK selector, not a semantic class |
| `.axles` | **NO** | **Must be DERIVED.** Group slots by `parsePositionStruct(id).axle` within `kind`, ordered by ascending `y` |
| `.slots` | YES | `tyres[]` |
| `.spareSlots` | **NO - and none exists** | Always empty. See 1.2 |
| `TyreSlot.positionId` | YES | `TyreDef.id` |
| `.axle` | **NO** | Derive via `parsePositionStruct(id).axle` (`:434-477`) |
| `.side` | **NO** | Derive via `parsePositionStruct(id).side` -> `L` / `R` / null |
| `.wheelType` | **NO** | Derive from `parsePositionStruct(id)`: `.kind` gives `steer`/`drive`/`lift`/`axle`/`spare`/`unknown` and `.role` gives `outer`/`inner`/`single` |
| `.x`, `.y`, `.width`, `.height` | YES | `x`, `y`, `w`, `h`. **Absolute, authored, non-negotiable** |

**Do not invent coordinates.** Every x/y/w/h in section 2's layouts is a
hand-placed literal that the artwork in `VehicleTyreDiagram.tsx` is drawn
around. A generative geometry engine will not line up with the bodies.

### 4.3 The single position parser

`parsePositionStruct` (`mobile/lib/tyreDiagramLayouts.ts:434-477`) is described
in its own header as the "single parser for BOTH id vocabularies". It returns
`{ kind, side, axle, role }`. Rule order is the contract:

| # | Pattern | Produces |
|---|---|---|
| 1 | `^SP(ARE)?\d*$` | `spare`, side null, axle 0, single |
| 2 | `^AXLE([LR])(\d*)$` | `axle`, side, axle = digits or 1, single |
| 3 | `^S([LR])(\d*)$` | `lift`, side, axle = digits or 1, single |
| 4 | `^F([LR])(\d*)$` | `steer`, side, axle = digits or 1, single |
| 5 | `^F(\d+)([LR])$` | `steer`, side, axle = digits, single |
| 6 | `^R(\d*)([LR])([OI])$` | `drive`, side, axle = digits or 1, role = O -> outer / I -> inner |
| 7 | `^R([LR])(\d*)$` | `drive`, side. **See the pairing rule below** |
| 8 | fallback | `unknown`, side null, axle 0, single |

Input is upper-cased, trimmed, and all whitespace, `-` and `_` removed before
matching (line 435).

**Rule 7 is the V3 pairing rule and it is not obvious.** For `RL1`..`RL4` /
`RR1`..`RR4`, the trailing number is the wheel ordinal across ALL drive wheels
on that side, and consecutive pairs form one dual axle (lines 461-474):

```
axle = ceil(k / 2)
first = (k is odd)
role  = side L ? (first ? outer : inner)
                : (first ? inner : outer)
```

So on the left, odd is outer and even is inner; **on the right it is mirrored** -
odd is inner, even is outer. That mirroring is what makes the rendered order run
outer-inner-inner-outer across a dual axle.

Rule ordering trap: rule 1 must precede rule 3, and rule 4 must precede rule 5.
`SP` is not a lift axle and `F1L` is not `FL`.

### 4.4 `mobile/lib/tyreLayout.ts` is unreferenced. Do not port it.

VERIFIED. Searching all of `mobile/` for `tyreLayout` yields exactly two hits
outside the file itself: an i18n key string
(`mobile/app/(app)/inspection/[id].tsx:163`, `t('modules.inspectionDetail.tyreLayout')`)
and a comment. **`buildTyreDiagramLayout`, `parsePosition` and
`resolveVehicleLabel` have zero call sites, and there is no test file for it.**

The spec's section 22 instruction to port `tyreLayout.ts` should be read as
covering the layout engine generally, not this specific module. Three reasons
not to port it:

1. It is a **generative** engine (constants at lines 61-88, placement at lines

   hand-authored coordinates. The two do not agree.
2. Its delegation is **partial**. Only `resolveVehicleLabel` delegates
   (line 153, to `resolveVehicleType`). Its `parsePosition` (line 104-127) is a
   **second, independent parser** with a different vocabulary
   (`trailer` where the canonical one says `axle`) and a different fallback
   (unknown becomes a left drive wheel at ordinal 99, rather than `unknown`).
   Porting both parsers reintroduces the drift this codebase spent effort
   removing.
3. Its `resolveVehicleLabel` special-cases `trailer` BEFORE delegating

**Its one genuinely useful contribution is documentation**: lines 12-14 state
"Position ids are never rewritten - they remain the storage keys for tyreData /

## 7. Flutter implementation notes

### 7.1 Rendering approach, per spec section 24

The Expo renderer is instructive: it draws the vehicle body and wheels as **SVG**
(`react-native-svg`), then lays **absolutely positioned `TouchableOpacity`
overlays** on top of each wheel for hit-testing
(`mobile/components/VehicleTyreDiagram.tsx:11-13`, `:1392-1403`). The overlay is
computed by `toScreen()` (`:1296-1304`), which adds 2 SVG units of padding on
every side purely as finger padding.

The recommendation for Flutter:

| Layer | Approach | Why |
|---|---|---|
| Vehicle body | **SVG asset** per `bodyKey`, 8 assets | The bodies are elaborate artwork with gradients. Re-authoring them as `CustomPainter` code is a large cost for no gain |
| Wheels | **`CustomPainter`** | 98 slots across 13 layouts, all simple rounded rectangles with a rim/glow/dark tri-tone. Painting is cheaper than 14 widgets |
| Hit targets | **Positioned widgets** over the painted wheels | Spec section 24 forbids "one giant static image with invisible buttons". These are not invisible buttons over a static image - each is a real widget over a slot whose geometry is known |

Coordinate transform, VERIFIED from `:1269-1274`:

```
viewBox   = (minX -10, minY -5, width 220, height viewH + 10)
scale     = renderWidth / 220
screenX   = (svgX - 2 - (-10)) * scale
screenY   = (svgY - 2 - (-5))  * scale
screenW   = (svgW + 4) * scale
screenH   = (svgH + 4) * scale
```

The `2` is `pad`; keep it, it is the finger padding. On top of that, ensure the
final hit rect is at least 48x48 logical pixels (Material minimum). A `Line pump`
dual wheel is 19x33 SVG units, which at a 300px render width is about 26x45
physical - **below the minimum on both axes**. The Expo app does not address
this; Flutter should, and the fix is to expand the gesture rect without moving
the painted wheel.

### 7.2 Per-slot state

Spec section 24 requires six states. What the Expo renderer actually provides,
VERIFIED:

| Spec state | Expo source | Notes |
|---|---|---|
| selected | `selectedPosition` prop (`:1237`) | present |
| condition | `CONDITION_RISK` (`:65-72`) maps the 6 conditions onto 4 risk bands: Good->good, Worn->warning, Damaged->critical, Puncture->critical, **Flat->warning**, Missing->none | present |
| installed / uninstalled | `recordedMap` (`:1288-1291`) | **partial - see the trap below** |
| inspection-complete | `pending` prop + `resolvePendingKeys` (`:46-56`), fed from a `tyreCompleteness()` result | present, and correctly accepts a result object, an array or a Set |
| touch target | `TouchableOpacity` overlay (`:1392`) | present, but see 7.1 on size |
| accessibility label | **absent** | No `accessibilityLabel`, `accessibilityRole` or `accessible` prop anywhere in the 1400-line component |

**The accessibility label must be BUILT, not ported.** Recommended value: the V2
canonical code plus the condition, for example `"LHCO, Good, pressure 110 psi"`,
because the V2 code is the name a fitter uses out loud. The V1 slot id is an
internal key and should not be spoken.

**Trap in `recordedMap`, VERIFIED at `:1288-1290`:**

```
recorded[t.positionId] = !!d && (
  !!d.serial_number || !!d.pressure_psi || !!d.tread_depth_mm ||
  !!d.notes || !!d.photo_uri || !!d.photo_url || d.condition !== 'Good'
)
```

This is a **truthiness** test, and it is the exact bug
`mobile/lib/tyreCompleteness.ts:214-217` documents and guards against:

> Compare against null, never truthiness: a pressure of 0 is a real reading on a
> flat tyre and `if (!pressure)` would silently discard it.

`TyrePositionData.pressure_psi` is typed `string`
(`mobile/lib/types.ts:99`), so a captured `'0'` is truthy and survives. But the
inspection detail screen reads `tyre_conditions` straight from the database
(`mobile/app/(app)/inspection/[id].tsx:87`), and if the stored JSON holds a
NUMERIC `0` then `!!0` is false and a flat tyre renders as "not recorded". It
also omits `checked`, so a wheel the inspector deliberately passed is drawn as
untouched.

**Rule for Flutter: implement "has evidence" ONCE, in the completeness engine
(`classifyEntry`), and have the renderer consume that result. Do not write a
second, weaker copy inside the widget.** Whether a numeric 0 is actually stored
is UNVERIFIED - see section 8.

### 7.3 RTL, per spec section 52

Spec section 52 requires that ids such as `FL` and `RR2` "should remain
technically readable and should not be accidentally reversed".

VERIFIED: `mobile/components/VehicleTyreDiagram.tsx` contains **no** `isRTL`,
`I18nManager` or direction handling. The diagram is direction-neutral today,
which is accidentally correct and must be made deliberate in Flutter.

Three rules:

1. **Never mirror the diagram under RTL.** `x` coordinates encode the physical
   vehicle. Left-hand-side wheels are `LH*` in the canonical code. Flipping the
   canvas would place `LHF1` on the right of the screen and send a fitter to the
   wrong wheel. Wrap the diagram in `Directionality(textDirection:
   TextDirection.ltr, ...)` and leave the surrounding chrome RTL.
2. **Force LTR on every position label.** `LHR1-O` under an RTL paragraph
   direction can render with the `-O` displaced. Set `textDirection:
   TextDirection.ltr` on each label `Text`, or wrap the string in U+200E.
3. **Do not translate a position id.** The i18n keys `positions.<id>` exist
   (referenced at `mobile/app/(app)/inspection/new.tsx:339`) and are for prose
   labels only; the stored key is never translated.

### 7.4 Do not hard-code serials into widgets

Spec section 23 says so, and the Expo renderer already obeys it: the widget takes
a `tyreData: Record<string, TyrePositionData>` prop (`:1236`) and looks up by
`positionId` with a fallback to `id` (`:1285`), which is what lets an older
record stored under the layout's internal id still light its wheel. Port that
double lookup.

### 7.5 Custom layouts are a real future requirement

`src/lib/vehicleDiagram.js` is the web's super-admin Vehicle Designer engine. Its
header (lines 9-16) states that `positionsFromConfig` emits a layout in the SAME
shape as the built-in entries, that "wheel slot ids reuse the component's
internal vocabulary (F1L, R1Lo, ...)" and that "labels use the canonical GCC
position codes ... so saved inspections keep matching". It supports 1-6 axles of
kind `steer`/`drive`/`trailer`/`lift`, 0-2 spares and 8 body styles.

RECORDED, PROJECT_MEMORY: `vehicle_diagram_configs` holds **0 rows**, "so letting
an admin-designed layout outrank the tyreless keyword is inert today and correct
later."

**Rule for Flutter: model `VehicleLayoutDefinition` as data from the start, with
the 13 built-ins as seed rows, so a database-sourced layout is a data change and
not a code change.** This is also what spec section 25 asks for when it says
layout "should ultimately come from vehicle/asset configuration rather than
scattered `if vehicleType == ...` conditions". Note the spare and lift support in
the designer is the reason `parsePositionStruct` handles `spare`, `lift` and
`axle` kinds that no built-in layout currently uses.
