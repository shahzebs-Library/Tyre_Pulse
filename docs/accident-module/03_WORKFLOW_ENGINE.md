> - `src/lib/accidentVocab.js` — every `canon*` / `toDb*` converter and option list.

>   `V398` (`accident_stage_events` ledger, `accident_stage_order` / `accident_stage_department`,
>   the **skipped-stage** concept, `basis` = observed|backfilled).
> - Capability model: `V229` (`app_user_can(key,cap)`, `user_access_grants`, resolver precedence),

> **Golden rules honoured throughout:** one lifecycle, one calc service, status is action-driven not a

> **mirrors** its SQL counterpart (the JS is the spec the DB copies, pinned by a test).

## 0. Architecture at a glance — two axes, one derivation

The case has **two orthogonal status axes** and they are already half-built:

| Axis | Granularity | Where it lives today | Role |
|---|---|---|---|
| **Workflow stage** | 12 coarse stages | `accidents.workflow_stage` + `accident_stage_events` ledger (V398) | the **ledger axis** — who is holding the case, how long, who skipped |
| **Case status** | 30 fine statuses | *new*: `accidents.case_status` (derived) | the **display headline** shown in the case header |
| **Workstream status** | per-workstream enum | *new*: `accident_case_workstreams` rows (computed from `accidents` columns until then) | the **truth** each team edits |

The design principle from the brief — *"Most status changes must be generated by completed actions, not
manually selected"* — is realised as a **one-way derivation**:

```
team action ─▶ workstream status changes ─▶ case_status re-derived ─▶ workflow_stage advances ─▶ V398 ledger event
```

Nobody sets `case_status` directly. It is a **projection** of the workstream statuses against the case's
**route** (§4). The coarse `workflow_stage` (which already drives the V398 ledger and department routing)
is the "current dominant stage" of that projection. `case_status` is the fine label the header shows.

This preserves every existing consumer: `stageFromStatus` / `statusFromStage` (the byte-mirror of V301)
keep mapping the legacy `status` column, and `accident_stage_events` keep recording occupancy on the
12-stage axis. The 30 statuses are a **finer overlay**, each one pinned to exactly one of the 12 stages.

### 1.2 Transition table — action-driven, not a dropdown

Each row is **from → to**, the **action** (the completed thing that triggers it), the **actor role /
capability** required, and any **guard** that must hold. A transition is only legal if (a) it is in this
table, (b) the actor holds the capability (§6), and (c) the guard predicate is true. There is **no free
"set status" control**; the register's severity/status edits are re-projected through §3, never written raw.

Legend for capability tokens (all on module `accidents`, §6): `create` `submit` `validate`
`approve_liability` `edit_insurance` `assess` `approve_repair` `request_parts` `execute_repair`
`qc_repair` `accept_handover` `post_cost` `close_case` `reopen_case` `cancel_case` `legal_hold`.

| *any* | `legal_hold` | Legal hold applied | `legal_hold` | reason recorded; SLA timers pause (§ pause reason "Legal hold") |
| `legal_hold` | *held status* | Hold released | `legal_hold` | — |
| `technical_assessment`/`insurance_review` | `total_loss_processing` | Total-loss route taken | `approve_repair` | total-loss approval workstream activated |

**Rules encoded above (do not weaken):**
- Every transition names a **completed action** and a **capability**, never "user picked it".
- `evidence_incomplete`, `rectification_required` are **return** states — they *reduce* progress, which
  is why completeness (§4) must be re-derived after every transition, not incremented.
- `operationally_completed → …` rows marked *(auto)* are **derived** by §3, not clicked.
- `cancelled_duplicate` and `legal_hold` are reachable from many states; both are audited and neither
  deletes data (brief §15: "Deleting an accident should not be allowed").

### 1.3 Pure function — the transition guard

Mirrors SQL `accident_case_transition_allowed(from, to)` (§3). Lives in `accidentCase.js`:

```js
// TRANSITIONS: Map<fromToken, Array<{ to, action, cap, guard }>>  (the table above, as data)
export function allowedTransitions(fromStatus) { return TRANSITIONS.get(fromStatus) || [] }
export function canTransition(fromStatus, toStatus) {
  return allowedTransitions(fromStatus).some((t) => t.to === toStatus)
}
export function transitionSpec(fromStatus, toStatus) {
  return allowedTransitions(fromStatus).find((t) => t.to === toStatus) || null
}
```

The register never writes a raw status: it calls an action service which (1) validates the action's own
fields, (2) checks `canTransition`, (3) checks `app_user_can('accidents', spec.cap)` client-side for UX and
the DB guard trigger for security (§6.3), (4) applies the workstream change, then (5) lets §3 re-derive
`case_status`.

## 2. Workstreams

### 2.1 Canonical workstream keys

Ten workstreams, chosen so each maps **1:1 to a closure requirement** (§5) and each already has an owning
team + owned columns in `accidentStages.STAGE_FIELDS`. They are a superset grouping of the brief's six
domains (A–F) and its finer §5 list (5.1–5.12).

| Key | Name | Domain | Owning team | Closure requirement it satisfies |
|---|---|---|---|---|
| `incident_evidence` | Incident & Evidence | A | Fleet Incident Officer | Incident registration + mandatory evidence |
| `fleet_validation` | Fleet Validation | A | Fleet Supervisor | Fleet validation |
| `liability` | Safety & Liability | B | HSE Officer / Fleet Mgr | Liability approved / NA |
| `insurance` | Insurance & Claim | C | Insurance Claims Officer | Insurance complete / NA |
| `assessment` | Technical Assessment | D | Workshop Planner | Technical assessment complete / NA |
| `repair` | Repair (decision → planning → execution) | D | Workshop | Repair route complete / NA |
| `workshop_qc` | Workshop Quality Control | D | Workshop QC | Workshop QC (where repair occurred) |
| `handover` | Fleet Off-road & Handover | E | Fleet Inspector / Ops | Fleet handover accepted |
| `finance` | Finance & Settlement | F | Finance / Cost Controller | Financial settlement complete |
| `corrective` | Corrective Actions | B | HSE Officer | Corrective actions complete |

> `repair` deliberately spans the decision, planning and execution sub-steps because they share the
> Workshop owner and one "repair route complete" closure test; the finer *statuses* (§1) still separate
> `repair_planning` / `awaiting_parts` / `repair_in_progress` for the header and the SLA clocks.

### 2.2 Per-workstream status enum (brief §7)

Twelve states, with tokens:

| Token | Label | Counts as satisfied? | Notes |
|---|---|---|---|
| `not_required` | Not required | **yes** (out of scope) | route did not include this workstream |
| `not_started` | Not started | no | in scope, untouched |
| `assigned` | Assigned | no | owner set, no work yet |
| `in_progress` | In progress | no | |
| `waiting_info` | Waiting for information | no | SLA pause reason applies |
| `waiting_approval` | Waiting for approval | no | |
| `waiting_external` | Waiting for external party | no | insurer/vendor/surveyor |
| `on_hold` | On hold | no | e.g. legal hold / vehicle unavailable |
| `completed` | Completed | **yes** | |
| `rejected` | Rejected | no | e.g. handover rejected → rectification |
| `reopened` | Reopened | no | previously completed, re-work required |
| `cancelled` | Cancelled | **yes** (out of scope) | workstream withdrawn with reason |

**"Not applicable"** is modelled as `not_required` **plus** a mandatory reason envelope (§5.3) — it is a
satisfied-but-out-of-scope state, distinct from `not_started`. This mirrors the existing `stage_waivers`
concept already in `accidentStages.stageApplies` / `waivedStages` (who / when / why is preserved on the
record). `not_required` and `cancelled` satisfy closure; `completed` satisfies closure; everything else
blocks it.

### 2.3 Source columns / tables each workstream reads

Two-tier design (near-term vs target-state), both honest:

- **Near-term (no new tables):** a workstream's status is **computed** from the existing `accidents`
  columns via `accidentStages.stageCompletion(record, stage)` — a workstream is `completed` when all its
  `STAGE_FIELDS[stage].required` fields are filled, `in_progress` when some are, `not_started` when none.
  This reuses the exact required-field map already in the repo.
- **Target-state (brief §12/§17):** an explicit `accident_case_workstreams` row per case per workstream
  holds the status set by team actions, the owner, the NA reason envelope and timestamps — so a team can
  say "waiting for insurer" without a column proxy. The computed value becomes the *fallback* when a
  workstream row is absent (migration-safe).

| Workstream | `workflow_stage` mirror | Required source (near-term columns → target tables) |
|---|---|---|
| `incident_evidence` | `reported` | `incident_date, asset_no, site, description` + mandatory `photos` / `documents` → `accident_evidence`, `evidence_requirements` |
| `fleet_validation` | `initial_review` | `responsible_owner_id, target_date` (validation acceptance flag) → `accident_case_workstreams` |
| `liability` | `hse_investigation` | `root_cause, corrective_action`, liability %/`fault_status`, `liability_approved_by`+`_at` → `liability_assessments`, `safety_investigations` |
| `insurance` | `insurance_claim` | `insurer, claim_amount`, `policy_no, claim_status, deductible, najm_status, taqdeer_status, gcc_liability_ratio` → `insurance_policies`, `insurance_claims`, `insurance_claim_documents`, `insurance_decisions`, `insurance_settlements` |
| `assessment` | `workshop_assessment` | `estimated_damage_cost, repair_type`, `workshop_name, expected_release_date` → `damage_assessments`, `damage_items` |
| `repair` | `repair_approval` + `repair_in_progress` | `approved_repair_amount, estimate_approved_by`, `repair_cost, parts_cost`, route → `repair_decisions`, `repair_orders`, `repair_tasks`, `parts_requests`, `purchase_orders`, `quotations`, `external_workshops` |
| `workshop_qc` | `repair_in_progress` (QC sub) | QC pass flag + checklist → `repair_quality_checks` |
| `handover` | `final_inspection` + `vehicle_release` | `closure_evidence`, `release_date`, actual downtime, accept/reject → `fleet_handover_inspections`, `vehicle_downtime` |
| `finance` | `cost_recovery` | `recovered_amount, recovery_status`, `recovery_source/date/reference, amount_transfer` + PO/invoice match → `financial_transactions`, `claim_recoveries` |
| `corrective` | `cost_recovery` (parallel) | `corrective_action, preventive_action` completion + evidence → `corrective_actions` |

### 2.4 Pure function — workstream status

Mirrors SQL `accident_workstream_status(record, workstream)`:

```js
// Reads an explicit workstream row if present, else derives from STAGE_FIELDS coverage.
export function workstreamStatus(record, workstream, rows = []) {
  const explicit = rows.find((w) => w.workstream === workstream)
  if (explicit) return explicit.status                              // team-set truth
  const stage = WORKSTREAM_STAGE[workstream]                        // → one of the 12 stages
  const c = stageCompletion(record, stage)                          // accidentStages.js (reused)
  if (c.total === 0) return 'not_required'
  if (c.complete) return 'completed'
  return c.filled.length > 0 ? 'in_progress' : 'not_started'
}
export const WORKSTREAM_SATISFIED = new Set(['completed', 'not_required', 'cancelled'])
export function workstreamSatisfied(status) { return WORKSTREAM_SATISFIED.has(status) }
```

## 3. Case-status derivation (the projection)

`case_status` is never written directly. `deriveCaseStatus(record, workstreams, route)` computes the
headline from the workstream states, honouring the case's route. Mirrors SQL
`accident_derive_case_status(...)`. It picks the **earliest unsatisfied required workstream** in pipeline
order and returns that workstream's characteristic status, unless a terminal/hold/branch flag overrides.

```
function deriveCaseStatus(record, wsRows, route):
    # 0. terminal + cross-cutting overrides win
    if record.legal_hold_active:            return 'legal_hold'
    if record.cancelled:                    return 'cancelled_duplicate'
    if record.reopened_flag:                return 'reopened'
    if record.total_loss_route:             return 'total_loss_processing'

    required = requiredWorkstreams(route)                 # §4
    status_of = { ws: workstreamStatus(record, ws, wsRows) for ws in ALL_WORKSTREAMS }

    # 1. draft / submission gate
    if not record.submitted:                              # incident not yet submitted
        return 'evidence_incomplete' if evidenceGaps(record) and record.returned else 'draft'
    if 'incident_evidence' in required and not workstreamSatisfied(status_of.incident_evidence):
        return 'evidence_incomplete' if record.returned else 'submitted'

    # 2. walk the required pipeline; first unsatisfied workstream sets the headline
    for ws in PIPELINE_ORDER intersect required:
        s = status_of[ws]
        if not workstreamSatisfied(s):
            return CASE_STATUS_FOR[ws][s]                 # e.g. insurance+waiting_external → awaiting_insurer_response

    # 3. everything required is satisfied → operationally / financially / fully
    if not financeSatisfied(status_of, required):         return 'insurance_settlement_pending' or 'financial_closure_pending'
    if not correctiveSatisfied(status_of, required):      return 'corrective_actions_pending'
    if not record.closure_review_approved:                return 'closure_review'
    return 'closed'
```

`CASE_STATUS_FOR[ws][wsStatus]` is a small lookup that turns a workstream's blocking state into the right
fine status, e.g.:

| workstream | `waiting_external` | `waiting_approval` | `in_progress` |
|---|---|---|---|
| `insurance` | `awaiting_insurer_response` | `claim_registration_pending` | `insurance_review` |
| `repair` | `awaiting_external_workshop` | `awaiting_fleet_approval` | `repair_in_progress` |
| `assessment` | — | — | `technical_assessment` |
| `handover` | — | — | `fleet_inspection` |

Once `case_status` is derived, `workflow_stage := CASE_STATUS_STAGE[case_status]` (unless null → keep
previous), and the existing V300 derive trigger + V398 ledger fire exactly as today.

## 4. Route-based completeness engine (`src/lib/accidentCase.js`)

> The single most emphasised rule in the brief (§4, §9, "Do not calculate completeness from all available
> fields"). Completeness is computed from **required workstreams only**, resolved from the case's **route**.

### 4.1 Routes

A **route** is the named path a case takes; it determines the required workstream set, required documents,
approvals, SLA targets, notification recipients and closure requirements. Routes are resolved by the
**business rule engine** (`workflow_route_profiles`, §8); `buildCaseRoute` is the deterministic **fallback
classifier** used when no admin rule matches, so the module never stalls waiting for configuration.

Core routes (extensible via config — do **not** hardcode the full matrix in core code):

| Route key | Trigger (fallback classifier) | Required workstreams |
|---|---|---|
| `minor_no_insurance` | minor severity, `insurance_involved=false`, movable, no injury | `incident_evidence, fleet_validation, liability, assessment, repair, handover, finance, corrective?` |
| `internal_repair_insurance` | insurance + `repair_type=Internal` | `incident_evidence, fleet_validation, liability, insurance, assessment, repair, workshop_qc, handover, finance` |
| `external_repair_insurance` | insurance + `repair_type=External` | `incident_evidence, fleet_validation, liability, insurance, assessment, repair, workshop_qc, handover, finance` (+ PO/quotation gates) |
| `total_loss` | total-loss route / assessment flag | `incident_evidence, fleet_validation, liability, insurance, assessment(survey), total_loss_approval, finance, asset_register` |
| `injury` | `injuries=true` or `injury_count>0` | `incident_evidence, authority_report, liability(HSE), medical_injury, insurance, management_review, corrective, legal?` |
| `third_party` | `third_party_involved=true` | base route **+** `third_party_recovery` in finance |
| `hit_and_run` | liability = Hit and run | `incident_evidence, authority_report, liability, insurance, assessment, repair, handover, finance` (no third-party recovery) |
| `glass_only` | type = glass-only | `incident_evidence, liability(lite), insurance?, repair, finance` |
| `no_damage` / `near_miss` | type = no-damage/near miss | `incident_evidence, liability, corrective` (no repair, no finance beyond zero) |
| `theft` / `fire` / `weather` | type match | `incident_evidence, authority_report, liability, insurance, assessment/total_loss, finance` |

A `?` marks a **conditionally required** workstream: required only if its toggle is on (e.g. `corrective`
required only when `corrective_action_required`; `workshop_qc` required only when a repair actually
occurred — brief §8.3 "workshop quality control complete **where repair occurred**").

### 4.2 Dimension mapping

The brief wants **five** percentages (§9): incident, insurance, repair, financial, overall. Each required
workstream belongs to a dimension:

| Dimension | Workstreams |
|---|---|
| `incident` | `incident_evidence, fleet_validation, liability, corrective` |
| `insurance` | `insurance` |
| `repair` | `assessment, repair, workshop_qc, handover` |
| `financial` | `finance` |
| `overall` | all required (weighted by satisfied count) |

### 4.3 Algorithm

```
function completeness(record, wsRows, route):
    required = requiredWorkstreams(route)                       # Set of workstream keys, incl. conditional resolution
    perDim = {}                                                 # dim → {required, satisfied}
    for ws in required:
        s   = workstreamStatus(record, ws, wsRows)
        ok  = workstreamSatisfied(s)                            # completed | not_required | cancelled
        dim = DIMENSION_OF[ws]
        perDim[dim].required  += 1
        perDim[dim].satisfied += ok ? 1 : 0
    result = {}
    for dim in ['incident','insurance','repair','financial']:
        d = perDim[dim]
        result[dim] = d.required == 0 ? null                    # honest null, NOT 100 — "no items in scope"
                                      : round(100 * d.satisfied / d.required)
    reqTotal = sum(perDim[*].required)
    satTotal = sum(perDim[*].satisfied)
    result.overall = reqTotal == 0 ? null : round(100 * satTotal / reqTotal)
    return result
```

**Non-negotiables baked in (from the reviewed engines):**
- A dimension with **no required items returns `null`, never 100** — same rule as
  `accidentStages.stageCompletion.pct` (100 reads as "this team finished" when nothing was in scope).
- Only **required** workstreams count; optional/out-of-scope workstreams are ignored, never padding.
- `not_required` (NA-with-reason) and `cancelled` count as **satisfied** — an NA workstream must not drag
  the percentage down (brief: "Fields marked Not Applicable must not simply be skipped" — they are
  *accounted for*, as satisfied, once a reason is on record).
- After **every** status transition (including return states `evidence_incomplete` /
  `rectification_required`) completeness is **re-derived from scratch** — never incremented — so a rejected
  handover legitimately drops the repair percentage.

## 5. Closure gate

### 5.1 Three closure levels (brief §8)

```js
export function closureLevel(record, wsRows, route):
    if record.case_status in ['closed']:                    return 'fully_closed'
    if operationallyComplete(record, wsRows, route):
        return financiallyComplete(record, wsRows, route) && correctiveComplete(...)
               ? 'fully_closed_pending_review'              # everything done, awaiting closure_review
               : 'financially_open'                         # vehicle back in service, money/CA outstanding
    return 'open'
```

| Level | Meaning | Vehicle | Money/claim/CA |
|---|---|---|---|
| **Operationally completed** | repair done, Fleet accepted, back in service | in service | may be open |
| **Operationally completed but financially open** | as above **and** claim/invoice/recovery/deductible/CA still pending | in service | open |
| **Fully closed** | every mandatory operational, insurance, financial, safety control complete + review approved | in service | closed |

"Operationally completed" = `handover` satisfied + `workshop_qc` satisfied (where repair occurred) +
`case_status ≥ operationally_completed`.

### 5.2 Not-Applicable envelope

A workstream (or a required field) marked Not Applicable must carry a **reason envelope** — this is the
existing `stage_waivers` shape extended, stored on the workstream row (or `stage_waivers[stage]` near-term):

```jsonc
// accident_case_workstreams.na_reason  (or accidents.stage_waivers[stage])
{
  "required": false,          // switches the workstream out of scope
  "reason":   "No third party involved; nothing to recover",
  "by":       "<user uuid>",  // WHO decided
  "at":       "2026-07-28T…", // WHEN
  "approved_by": "<uuid|null>"// approval WHERE the route/rule demands one
}
```

A workstream is only treated as `not_required` (satisfied) when `reason` **and** `by` **and** `at` are
present, and — where the route's closure profile flags `na_requires_approval` — `approved_by` is set. A
bare "switched off" with no reason does **not** satisfy closure. `waivedStages()` already surfaces these
for the audit view; extend it to workstreams.

### 5.3 The Fully-Closed boolean AND (brief §8.3)

`canFullyClose(record, wsRows, route)` returns `{ ok, blockers }` where `ok` is the exact conjunction:

```
ok =  workstreamSatisfied(incident_evidence)          # incident registration + mandatory evidence complete
  AND workstreamSatisfied(fleet_validation)
  AND (liabilitySatisfied           OR markedNA(liability,   approved))
  AND (workstreamSatisfied(insurance) OR markedNA(insurance, approved))
  AND (workstreamSatisfied(assessment)OR markedNA(assessment,approved))
  AND (repairSatisfied              OR markedNA(repair,      approved))
  AND (workshopQcSatisfied          OR not repairOccurred)          # QC required only where repair happened
  AND handoverAccepted                                             # Fleet handover accepted (not merely workshop complete)
  AND workstreamSatisfied(finance)                                 # financial settlement complete
  AND correctiveComplete                                           # corrective actions complete (or NA w/ reason)
  AND noOverdueMandatoryTask(record)                               # no mandatory task overdue & unresolved
  AND noPendingApproval(record)                                    # no approval still pending
  AND noMissingRequiredDocument(record, route)                     # no required document missing
  AND noOpenWorkstream(record, wsRows, route)                      # no required workstream still open
  AND closureReviewApproved(record)                                # closure review approved
```

`blockers` is the list of clauses that failed, each `{ workstream|check, reason }` — the same shape as
`caseProgress().outstanding`, so the Overview "closure blockers" panel and the closure screen both render
from it. `canFullyClose` is enforced **on the server** (the `close_case` guard trigger, §6.3) so a
malicious API call cannot skip it (brief acceptance criterion 24, §31 "user cannot bypass closure
requirements through API calls").

### 5.4 Read-only after close + controlled reopen (brief §8, §15)

- On `closed`, the case becomes **read-only**: an RLS `UPDATE`/write policy denies any change to a case
  whose `case_status = 'closed'` **except** a reopen action (which itself requires `reopen_case`).
- **Reopen requires**: reopening reason, requested-by, approved-by, new assigned owner, new due date, and a
  full audit record — enforced by the reopen action + guard trigger. On reopen, `case_status = 'reopened'`
  then the previous blocking status; the V398 ledger records the reopen as a fresh stage occupancy
  (a stage visited twice legitimately, already handled by `caseProgress` "visits").
- **Never a hard delete** — a bad case is `cancelled_duplicate` with a link to the primary case.

### 6.3 Enforcement (reuses the repo's capability model — no parallel system)

Three layers, all existing patterns:

1. **`app_user_can('accidents', <cap>)` (V229)** — the resolver: Admin/super ⇒ true, else
   `revoke > role default > grant > deny`. Role defaults come from `module_permissions` rows (per
   `profiles.role`, Title Case) for `view`; non-view capabilities read the `app_settings.permission_overrides`
   envelope. Per-user exceptions ride `user_access_grants` (grant/revoke, expiry-aware) — so one insurer
   can be given `edit_claim` for a single site without a migration.
2. **RLS PERMISSIVE write policies** (the V238/V241 pilot pattern) — each accident-family table gets an
   `INSERT/UPDATE/DELETE` PERMISSIVE policy `USING (app_user_can('accidents', '<cap>'))`, ORed with the
   role policies so it only *adds* access to granted users and is scoped by the existing org + country +
   site RESTRICTIVE isolation. This is the real boundary; the client checks are UX only.
3. **Status-change guard trigger** — generalise `enforce_status_change_capability` (V242) into
   `enforce_accident_action_capability()`: a BEFORE UPDATE trigger on `accidents` that, for each detected
   action (a `case_status` change, a liability approval, a claim edit, a cost post, a close, a reopen),
   requires the **specific** capability for that action and rejects with `42501` when the caller lacks it
   or the transition is not in `TRANSITIONS`. This is what stops an API caller skipping the state machine
   (brief §31). The `close_case` branch additionally calls `accident_can_close(...)` and raises if `ok` is
   false — the server-side twin of §5.3.

```sql
-- sketch, mirrors V242 shape
create or replace function public.enforce_accident_action_capability()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  if NEW.case_status is distinct from OLD.case_status then
    if not public.accident_transition_allowed(OLD.case_status, NEW.case_status)
       then raise exception 'Illegal status transition % -> %', OLD.case_status, NEW.case_status using errcode='42501'; end if;
    if not public.app_user_can('accidents', public.accident_transition_cap(OLD.case_status, NEW.case_status))
       then raise exception 'Not permitted to perform this action' using errcode='42501'; end if;
    if NEW.case_status = 'closed' and not (public.accident_can_close(NEW.id)).ok
       then raise exception 'Closure requirements not met' using errcode='42501'; end if;
    if not public.accident_sod_ok(NEW.id, OLD.case_status, NEW.case_status, auth.uid())
       then raise exception 'Segregation of duties: same user cannot perform this step' using errcode='42501'; end if;
  end if;
  -- closed cases are read-only except a reopen action
  if OLD.case_status = 'closed' and NEW.case_status <> 'reopened'
     and row(NEW.*) is distinct from row(OLD.*)
     then raise exception 'Closed case is read-only' using errcode='42501'; end if;
  return NEW;
end $$;
```

### 6.4 Segregation of duties

Rule (brief §15, §35): **the same person cannot register the accident, approve liability, approve repair
and close the same case**. Enforced by `accident_sod_ok(case, from, to, uid)` inside the guard:

- `approve_liability`: `uid ≠ accidents.created_by`.
- `approve_repair`: `uid ≠ liability_approved_by`.
- `close_case`: `uid ∉ { created_by, liability_approved_by, estimate_approved_by }`.

The actor of each controlled step is recorded (`created_by`, `liability_approved_by`, `estimate_approved_by`,
`closure_approved_by`) so the check is data-driven and auditable. A tiny single-team org can be granted an
explicit `sod_override` capability (audited) rather than silently weakening the rule.

## 7. Loops (repair / insurance / closure)

The state machine is not strictly linear; three loops are first-class (brief §20) and every loop re-enters
a *return* status that **re-derives** completeness downward:

- **Repair loop:** `repair_in_progress → workshop_quality_inspection → fleet_inspection → (reject)
  rectification_required → repair_in_progress → …`. Each visit is a fresh `accident_stage_events` occupancy
  (`caseProgress` already sums time across "visits" for a re-worked stage).
- **Insurance loop:** `claim_registration_pending → awaiting_insurer_response → (insurer requests docs) →
  awaiting_insurer_response → …` with a missing-document task per cycle.
- **Closure loop:** `closure_review → (blocker found) → <failing workstream status> → … → closure_review`.
  `closureBlockers()` names the failing workstream so the case returns to the right owner, not to the start.

Because completeness (§4) is recomputed from scratch after each transition, a loop back correctly lowers the
percentages instead of leaving a stale high number — the property the brief demands ("Do not calculate
completion as fields filled").

## 8. Business-rule engine (`country_rule_profiles` / `workflow_route_profiles`)

Keep routes, required fields/docs/workstreams, approvals, SLA targets, recipients and closure requirements

```jsonc
    "working_calendar": "KSA", "currency": "org.currency"
  }

```

### 8.3 How the engine consumes it

- `buildCaseRoute(record, ruleProfiles)` — pick the winning `workflow_route_profiles` row (else the
  deterministic fallback classifier §4.1); returns `{ key, source, profile }`.
- `requiredWorkstreams(route, record)` reads `profile.required_workstreams` (resolving conditionals against
  the record) — so **adding a route is a config row, not a code change**.
- `completeness` / `canFullyClose` read `profile.required_documents` + `closure_requirements` for the
  missing-doc and closure checks.
- The **SLA engine** reads `profile.sla` + `country_rule_profiles.working_calendar` (brief §15/§10). Every
  timer keeps start/due/remaining/owner/pause-reason/resume/escalation; a pause requires a reason **and** an
  expected follow-up date (brief: "Users must not be able to pause a timer without selecting a reason").
  Regulatory maxima (KSA: 9 / 5 / 45 working days) are stored as **configurable controls**, and internal
  targets are much shorter — never hardcoded, never the same value for two countries.
- The **notification + escalation** engine (brief §26) reads `profile.recipients` through the *existing*
  `evaluateRouting` + `resolveRecipients` (accidentWorkflow.js) + the V300 `consume_event_accident_notify`
  domain-event consumer — no parallel bus. Escalation levels L1–L4 (before-due → overdue → dept manager →
  senior management for injury/fatality/total-loss/rejection/dispute/overdue-settlement) are thresholds on
  the SLA instance, configurable per profile.

An **admin UI** edits these profiles (brief §27) so a new GCC country is a set of rows, never a code branch —
matching the repo's existing "config not code" pattern (`accident_routing_rules`, `country_currency`,
`site_aliases`).

## 10. Acceptance checks for this engine (traceable to brief §32)

1. A status only changes via a listed transition whose action completed and whose actor holds the
   capability (no free dropdown). — §1.2, §6.3
2. Each workstream shows its own status; the case header shows the derived headline. — §2, §3
3. Completeness is computed from required workstreams only; a no-scope dimension shows `null` (N/A), never
   100. — §4.3
4. NA requires reason + user + date (+ approval where the profile demands). — §5.2
5. Fully-closed requires the full §5.3 conjunction; an API call cannot skip it (server guard). — §6.3
6. Closed cases are read-only; reopen needs reason + approval + new owner + due date + audit. — §5.4
